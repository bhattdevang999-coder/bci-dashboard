## What changed at the schema level

| | v1 (TLG-internal) | v2 (Amazon-shaped) |
|---|---|---|
| Identity | STYLE#, MODEL NUMBER, SKU, CHILD ASIN, TLG Style Desc | STYLE#, STYLE NAME, Brand Code |
| Classification | Inferred from TLGDIV NAME + Sub-Class | Explicit: Department, Age Range, Target Gender, Sub-Class |
| Material | Single cell "95% Polyester, 5% Spandex" | Material 1 / 2 / 3 + Fabric Content Percentage |
| Closure | Single cell "Zipper" | Closure Type + Closure Type 2 |
| Sleeve | Sleeve Type only | Sleeve Type + Sleeve Length |
| Item length | Inferred from CBL (inches) | Explicit Item Length Description (Amazon vocab) |
| Columns | 31 mixed | 33 Amazon-only |

The "27 cols" estimate in the sprint plan turned out to be 33 once I laid them all out — I kept all five bullet columns explicit (5 cols), Removable Hood (operator-supplied), and Number of Pockets. Still Amazon-attribute-shaped, no TLG-internal mix.

**Dropped from v2:** TLGDIV NAME, TLG Style Desc, MODEL NUMBER, SKU, CHILD ASIN. The first three were operator references that didn't drive Amazon ingest. SKU is auto-derived from Brand Code + STYLE#. CHILD ASIN moves to an optional "Existing Listing" lookup, not the upload template.

**Added in v2:** Department (explicit), Age Range (explicit), Target Gender (explicit), Item Length Description (explicit Amazon vocab), Sleeve Length (was missing entirely in v1), Material 2, Material 3, Closure Type 2.

## The mapping layer

Lean implementation — the importer's `_HEADER_ALIASES` already does the work. v2-specific aliases (`age_range`, `target_gender`, `item_length_description`, plus Pass 3's `material_2`, `material_3`, `closure_2`) are no-op on v1 ingest (the columns aren't there → `row_data.get(...)` returns None → state filter drops them).

The only new code outside aliases:

- **`detect_template_version(header_row) -> 'v1' | 'v2' | 'unknown'`** — signal-header lookup. v2 wins if a v2 signal is present (the v2 ingest path is a superset of v1; legacy TLG columns are ignored when present alongside v2 columns).
- **`style_to_form_state` reads v2 explicit columns when present:**
  - `target_gender` (v2 column) → `target_gender#1.value` (wins over inferred)
  - `age_range` (v2 column) → `age_range_description#1.value` (defaults to "Adult" on v1)
  - `item_length_description` (v2 column) → `item_length_description#1.value` (wins over CBL-inches derivation)

`material_2` / `material_3` / `closure_2` already wired in Pass 3.

## Honest limits

1. **Template version detection is signal-header-based.** If an agency sends a template with both v1 AND v2 columns (e.g., they kept TLGDIV NAME alongside Department for backward compat), the detector returns v2 — by design. That means v1-internal columns are simply ignored. Operators should know this; documented in the `detect_template_version` docstring.
2. **No xlsm export changes.** The xlsm writer (in `app.py:5400-6500`) is unchanged. v2 ingest still produces the same Amazon xlsm output as v1 ingest — the difference is only in the source-side parser, not the destination.
3. **The fixture is one row.** Real v2 ingest will get multi-row pressure-tested when the agency's next batch lands. The QA exercises every field, but doesn't exercise scale.
4. **No backward conversion utility.** If an operator has a stockpile of v1 templates and wants to convert them all to v2, that's a separate utility — not built. Both formats parse, so they don't need to convert.
